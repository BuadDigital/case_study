# design-sync notes — @platform/ui-kit

## Repo-specific gotchas

- **No dist/build for ui-kit.** `packages/ui-kit` ships raw TypeScript (`exports['.'] = "./src/index.ts"`), consumed directly by the Next.js app via workspace resolution. No `build`/`prepare` script exists. Per user decision, the converter synthesizes the entry from `src/index.ts` directly — `.d.ts` prop contracts are weaker than a real declaration build would give (no `buildCmd` set; nothing to run).
- **Tailwind v4, no static compiled CSS ships with ui-kit.** Styling is utility classes (`className="bg-surface text-text-2 ..."`) resolved at *app* build time by Tailwind v4's `@source` scan (see `apps/shell/src/app/globals.css`) plus a `@theme inline` block mapping ui-kit's CSS custom properties (`packages/ui-kit/src/styles/tokens.css`) to Tailwind theme tokens (`--color-surface`, `--color-danger`, etc.). ui-kit alone has no compiled stylesheet.
  - **Fix**: `.design-sync/scripts/compile-tailwind-css.mjs` runs `apps/shell/src/app/globals.css` (the real entry — `@import "tailwindcss"` + the full `@theme` block + `@source` globs) through `@tailwindcss/postcss` and writes `packages/ui-kit/.ds-sync-cache/ui-kit-tailwind.css` (gitignored). `cfg.cssEntry` points there — **`cssEntry` is resolved relative to `PKG_DIR` and must physically stay inside `packages/ui-kit/`** (the converter enforces this — content is inlined into the shipped bundle), which is why the output can't live under the repo-root `.design-sync/`.
  - **Re-run this script before every build/resync** — it is not wired into any `buildCmd` since it isn't a package build, just re-run `node .design-sync/scripts/compile-tailwind-css.mjs` manually first.
  - All `cfg.*` path fields (`cssEntry`, `extraFonts`, `componentSrcMap` values, etc.) resolve **relative to `PKG_DIR` (packages/ui-kit)**, not the repo root — `extraFonts` may point outside the package with `../../` as long as it stays inside the git workspace root; `cssEntry` may not leave the package at all.
- **Tajawal (Arabic brand font) is loaded via `next/font/google`** in `apps/shell/src/app/layout.tsx` (`--font-arabic` CSS variable) — Next self-hosts subsetted woff2s under `.next/static/media/` at app-build time, which is a gitignored, machine-local cache, not a stable path to point `extraFonts` at.
  - **Fix**: downloaded the real Tajawal woff2s (400/500/700, arabic+latin subsets) directly from Google Fonts' CSS2 API (`fonts.googleapis.com`/`fonts.gstatic.com` — Tajawal is SIL OFL licensed, public) into `.design-sync/fonts/` (committed), with a self-contained `tajawal.css` pointing at the local files. Wired via `cfg.extraFonts`.

## Known render warns / preview-authoring findings (folded from wave learnings, 2026-09-17)

All 86 components authored (6 solo calibration + 8 subagent batches — forms, table-cells, modal, status/icons, page-layout, stats/KPI, misc-utility, tabs/toolbar). Final: 84/86 graded "good", 2 left as honest floor cards (ModalOverlay, AppModal — GoogleMapPin also floor-card, see below), 0 broken.

- **`ModalOverlay` / `AppModal`** — both use `position: fixed; inset: 0` (a real full-viewport overlay; `AppModal` wraps `ModalOverlay`). Both were authored with realistic dialog content and initially APPEARED to work after a `cfg.overrides.<Name>: {"cardMode": "single", "viewport": "..."}` fix (tried 480x360, then 560x560 for AppModal) — `render-check.json`'s mechanical check even reported `ModalOverlay` as `bad: false` with the correct extracted `texts`. **This was misleading**: the numeric/text-extraction check passed because the real DOM text is present in the page, but the actual rendered PIXELS are blank for both — confirmed by actually opening `_screenshots/review/general__ModalOverlay.png` and the raw per-cell screenshot, both essentially empty (a faint 1px gradient line, nothing else). Don't trust `render-check.json`'s `bad`/`texts` fields alone for `position: fixed` components — always open the actual screenshot. No `cardMode`/`viewport` combination fixed the underlying collapse (2 honest attempts each). **Resolution: deleted both authored previews**, letting them fall back to the converter's own floor card (an honest typographic "preview not yet authored" block) — same treatment as `GoogleMapPin` below. The bundle still ships both fully functional (real `.d.ts`, real exports); the six underlying `Modal.*` pieces (`ModalCard`/`Header`/`Title`/`Close`/`Body`/`Footer`) all preview correctly and fully represent the dialog's visual language on their own. If revisited: investigate why a `position: fixed` element's painted content isn't captured within a `cardMode: single` cell at all — likely a capture-harness limitation with fixed-position elements generally, not specific to this DS.
- **`RowMoreMenu`** — flagged `[GRID_OVERFLOW]` (its open dropdown, simulated via a mount-time click, escapes the multi-card grid layout). Resolved with `cfg.overrides.RowMoreMenu: {"cardMode": "single", "primaryStory": "Default"}`.
- **`GoogleMapPin`** — renders completely blank in the offline capture browser: it calls `loadGoogleMapsApi()`, which injects a live `<script src="https://maps.googleapis.com/...">` that never resolves without network access, so the component sits forever in its initial empty state. This is a genuine network dependency, not a styling bug. Tried `cfg.overrides.GoogleMapPin.skip` (its only story) but that just produces an empty card since ALL its stories were skipped — `skip` is for dropping some stories from a multi-story component, not zeroing out a single-story one. **Resolution: deleted the authored `.design-sync/previews/GoogleMapPin.tsx` entirely**, letting it fall back to the converter's own floor card (a deliberate typographic "preview not yet authored" block), which renders non-empty and passes the render check cleanly — more honest than a blank white box anyway. The component still ships fully functional in the bundle (real `.d.ts`, real exports); it's just unauthored. Would need a mocked/offline Maps stub upstream to ever author a real static preview for it.
- **Confirmed benign `[RENDER_THIN]`/`[RENDER_BLANK]` warns** (verified by opening the actual screenshots — all show correct, fully-styled content; the checker's text/height heuristics just don't recognize small SVG-only icons or components whose visible content is graphical, not textual): `EmptyIconSearch`, `EmptyIconBuilding`, `KpiAlertIcon`, `KpiCheckIcon`, `KpiClipboardIcon`, `KpiClockIcon`, `ShowAllEye`, `MobileKpiStatCards` (this last one carries an existing "good" grade from its captured review screenshot — a *different*, full-bundle validate-only screenshot render showed an empty box, but the actual graded review capture is correct; treat this as a known validate-vs-capture rendering-path quirk for this component, not a real defect). A re-sync should NOT be alarmed by these same warn lines recurring.
- **`InfathSelectField`** sets `appearance-none` on the native `<select>` with no custom chevron — visually indistinguishable from `InfathTextField` in a screenshot even though it's a real `<select>`. Informational only, not touched (component behavior, not a preview bug).
- **`RowMoreMenu`** has no `open`/`defaultOpen` prop and the capture harness has no interaction step. Worked around entirely in the preview file with a `useEffect` that clicks the trigger button on mount so the open menu is captured. No library code changed. A `defaultOpen` prop would be a reasonable upstream addition.
- **Brand token mapping is non-obvious — don't mistake these for bugs on a future re-sync**: in `packages/ui-kit/src/styles/tokens.css`, `--success` maps to `--ink` (dark navy, not green) and `StatCard accent="blue"`/`accent="green"` render gold/navy respectively (Ejadah's brand palette, not semantic-literal colors). `ProgressBar`'s "complete" (100%) state is therefore navy, not green — correct per the DS's actual tokens.
- **`GentleBusy`/`GentleLoadingCopy`/`PanelSkeleton`/`InlineLoadingSkeleton`/`PageLoadingHint`** all route through `useDeferredVisible` (300ms delay). Turned out to be a non-issue: `package-capture.mjs` only fixes `Date.now()`, it doesn't pause real timers, and the capture loop's `networkidle` + settle wait comfortably exceeds 300ms — loading content reliably renders. No workaround needed.
- **`EmptyIconSearch`/`EmptyIconBuilding`** bake in `opacity-60` — intentionally muted/gray by design, not a sizing/color bug.
- **`ShowAllEye`**'s closed state renders as a thin lid line by design (per its own docstring), not a slash or full glyph.
- **`StatusBadge`**'s `status` prop is a fixed dictionary key (no free text), and has no direct "مسودة"(draft) entry — the closest available key (`under_study` / "قيد الدراسة") was used as a stand-in in its preview.

## Re-sync risks

- The compiled Tailwind CSS (`cssEntry`) and the Tajawal font files are **not derived from ui-kit's own build** — they're pulled from the app shell's global stylesheet and Google Fonts respectively. If `apps/shell/src/app/globals.css`'s `@theme` block changes (new color tokens, renamed CSS vars) or ui-kit starts using Tailwind utility classes not yet covered by the app's current `@source` scan, re-run `compile-tailwind-css.mjs` before syncing — a stale cached CSS silently under-covers new classes.
- If a component is added to ui-kit whose only usages of a given utility class live in files the `@source` glob doesn't cover (unlikely given it scans all of `apps/**` and `packages/**`), that utility won't compile — watch for unstyled previews on new components.
- `dtsPropsFor`/`componentSrcMap`/`libOverrides` overrides accumulated during the verify loop (if any) must be preserved on every re-run of this config — never wholesale-replaced.
